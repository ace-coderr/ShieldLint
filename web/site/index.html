01 The problem

Zcash privacy is opt-in.
Code decides it.

Shielded transactions are the default in the protocol, but not in the integrations. Three failures account for most real leaks — and none of them is a compile error, a failing test, or something code review reliably catches.

01 / TRANSPARENCY

Transparent recipients

One t1… address in a payout path makes the amount, sender and recipient public forever. It compiles, tests green, and is invisible in review.

Caught by SL001 · SL003 · SL008

02 / EXPOSURE

Data in the wrong place

Memos carry invoices and customer identity. Viewing keys decrypt an entire account. Both end up in logs and error trackers because a string is just a string.

Caught by SL004 · SL005 · SL006 · SL007

03 / ENCODING

Encoding mistakes

A truncated address or an invalid ZIP 321 request is a checkout that fails — or worse, funds sent somewhere unspendable. Neither surfaces until production.

Caught by SL010 · SL011 · SL012 · SL014

02 How it works

Three passes.
No network, no guessing.

ShieldLint is a static analyser, not a pattern matcher. It lexes the file, decodes every candidate with the real specifications, and only then decides whether a rule applies.

01

Find the candidates

A language-aware lexer skips comments, understands Python/C string concatenation, JS regex literals, Rust raw strings and char literals, then pulls out every string.

Python · JS/TS · Rust · Go · Java · C/C++ · YAML

02

Decode with the specs

Bech32m, F4Jumble, ZIP 316 receivers and typecodes, ZIP 321 parameters, Base58Check, Sapling and Sprout. A malformed literal is provably malformed, not probably.

14.6k test vectors · byte-for-byte round trips

03

Report with evidence

Each finding carries the file, line, column, the decoded value, why it leaks and how to fix it — as text, JSON, SARIF or GitHub annotations.

exit 1 on error · suppressible · deterministic

Six of the fourteen rules.

Every rule is tied to a specification and ships with a rationale, a bad example, a fixed example and references. A finding names the consequence, not just the line.

SL001 · ERROR privacy lost

Payment to a transparent address

Amount, sender and recipient become public on-chain. The single most common way a Zcash integration leaks — often through a named constant, not a literal.

- REFUND = "t1cN2ZVWzWcVRrnfeQzmkpLhzQ4dYRv8yRY" + REFUND = "u1…" # shielded recipient
SL003warning

UA with a transparent receiver

A u1… address that also carries a t1… receiver lets a sender quietly downgrade the payment to public.

SL006error

Viewing key in source

A Unified Full Viewing Key decrypts every incoming note it covers — including the memos that carry invoices and identity.

SL011error

Invalid payment request

ZIP 321 is strict: a memo on a transparent recipient, a leading-zero parameter index, a duplicate amount — all rejected by wallets.

SL012error

Memo over 512 bytes

Memos are always 512 bytes, padded with zeros. An oversized literal silently truncates or bricks the payment.

SL008warning

Transparent spend source

Spending transparent UTXOs links inputs to outputs. Prefer a shielded pool unless the user explicitly chose otherwise.

Tests in CI

What the tests cover

  • Round-trip fidelity. Decoding then re-encoding must produce the original string — this catches typos that a decoder would happily accept.
  • Rejection. Every invalid example in ZIP 321 must fail, and fail for the documented reason.
  • Self-lint. ShieldLint runs on its own source in CI and must report nothing.
  • Real trees. Run over librustzcash (382 files) without a crash; findings concentrate in vendored vectors.

Privacy posture

  • No network at scan time. Nothing is fetched, nothing is resolved, nothing is validated online.
  • No telemetry. The web UI analyses in memory and discards; no accounts, no storage, no logs of pasted code.
  • Keys are never used. Viewing keys are parsed as data, never as credentials — an exposure is reported, never exercised.
