Validate a ZIP 321 payment request

A zcash: URI is what a checkout hands to a wallet. ZIP 321 is strict about it, and a request many wallets reject is a payment nobody can make. Paste one to see every parameter and every violation.

Result

Paste a zcash: URI and press Validate.

01 Reference

The parameters that matter.

Everything the validator checks, and the ones that change whether a payment leaks. Full grammar is in ZIP 321.

ParameterRuleWhat goes wrong
address / address.NRequiredA request with no address, or an index starting at address.0, is invalid.
amountOptionalDecimal ZEC, no exponent, no currency suffix, at most 8 decimals, exactly one per payment.
memoOptionalUnpadded base64url, at most 512 bytes, and it requires a shielded recipient.
labelOptionalFree text shown to the user. Ignored by wallets that do not support it.
messageOptionalFree text. Do not put personal data here — nothing encrypts it.
req-*Unknown = invalidA required parameter a wallet does not understand must make the whole URI fail.
other *IgnorableUnknown optional parameters are skipped, so tracking parameters survive.

Three invalid requests

# memo cannot ride a transparent address
zcash:t1…?amount=1&memo=b3JkZXI6MQ

# indexes start at 1, never 0
zcash:zu1…?address.0=u1…

# one amount per payment
zcash:zu1…?amount=1&amount=2

Why it is a privacy rule

A memo is encrypted to the recipient, but only for shielded recipients. On a transparent address there is no memo field at all, so wallets either drop it or leak it into a public transaction. SL010 and SL011 both key off this.

The validator also flags a request whose only recipient is a transparent address, even when the syntax is perfect — because a correct URI can still be a public payment.
